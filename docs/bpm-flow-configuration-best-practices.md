# BPM 流程图配置最佳实践

> 版本：2026-11-04  
> 适用范围：根据独立业务输入设计规范化流程图，并通过 `eadp bpm graph` 校验、预览和导入。  
> 核心原则：**输入不限格式，语义必须明确；不确定就提问，不猜节点、不猜条件、不猜执行人。**

## 1. 目标与事实来源

本规范把人工完成稿中可复用的配置范式沉淀到 CLI，使 AI 不再依赖某个参考实现。业务输入可以是规则说明、结构化表格、既有设计稿、页面/接口契约或目标环境只读查询结果；输入采用何种文件格式不影响节点选择。

发生信息差异时，按以下顺序处理：

1. **当前业务需求及用户确认**：决定实际审批规则，不由历史样例覆盖。
2. **`eadp bpm graph nodes`**：决定节点类型、场景、必填配置、连线和迁移约束。
3. **`eadp bpm graph conditions`**：决定目标环境业务实体发布了哪些判定条件字段，网关条件只能使用这些变量。
4. **目标环境只读查询**：决定人员、岗位、组织、页面、接口等实际绑定。
5. **外部设计稿**：只作为业务意图或配置范式参考，不作为目标环境依赖存在的证据。

任何一项不能唯一确定时，先输出具体的待确认问题；不得用“通常如此”继续生成或写入。

## 2. 开始画图前必须明确的业务事实

至少整理以下内容：

- 流程启动条件、正常完成条件；
- 每个业务步骤是办理、审批、会签、自动服务、等待触发还是子流程；
- 步骤的先后关系，哪些步骤可跳过，哪些可叠加或并行；
- 每个条件使用的变量、类型、允许值、空值语义、比较符和默认路径；变量取自 `eadp bpm graph conditions`，系统未发布的字段先提问；
- 每个人工节点的执行人类型、业务键和工作页面；
- 审批/会签的同意、不同意分别去哪里；
- 驳回是否允许修改，修改后从头重审还是返回指定环节；
- 结束前后是否有服务事件、人工抄送或独立子流程；
- 目标是新建定义还是更新哪个既有定义。

缺少上述信息并不总是需要一次问完，但**在相关信息影响节点选择或连线时，必须先问再画**。

## 3. 节点选择：按业务语义，不按名称猜测

完整的逐节点指导随 CLI 发布：

```text
eadp bpm graph nodes
eadp bpm graph nodes --kind Approve
eadp bpm graph nodes --kind CounterSign
eadp bpm graph nodes --kind ExclusiveGateway
```

输出的 `usage` 包含：

- `summary`：节点表达什么；
- `exampleScenarios`：适用示例；
- `notFor`：明确不适用的情况；
- `requiredInputs`：选择前必须掌握的信息；
- `askWhenUnclear`：不确定时应提出的问题。

### 3.1 人工任务

| 业务场景 | 节点 | 选择边界与必问项 |
| --- | --- | --- |
| 修改、补充资料、人工抄送等普通办理 | `Normal` | 不产生同意/不同意双分支；确认执行人、页面和完成去向 |
| 一人确认或办理，只有完成结果 | `SingleSign` | 不是“只有一个审批人”的同义词；存在不同意结果时评估 `Approve` |
| 单个审批决策 | `Approve` | 恰好两条出口；确认审批人、同意去向、不同意去向 |
| 多人在同一环节共同决策 | `CounterSign` | 确认并行/串行、通过比例及两种结果；有明确先后角色时拆成多个 `Approve` |
| 节点内并行办理且不按票数决策 | `ParallelTask` | 先与 `CounterSign`、`ParallelGateway` 区分；不能确认时必须提问 |
| 节点内依次办理 | `SerialTask` | 先确认是否应拆成多个有独立业务含义的审批节点 |
| 工作池成员领取任务 | `PoolTask` | 确认池代码、领取规则、页面和服务接口 |
| 线下或占位动作 | `ManualTask` | 不得用来掩盖尚未明确的业务规则 |
| 智能体完成任务 | `AgentTask` | 确认执行人、模板、超时、服务及结果处理 |

### 3.2 自动、等待和子流程

| 业务场景 | 节点 | 选择边界与必问项 |
| --- | --- | --- |
| 立即执行的系统自动动作 | `ServiceTask` | 确认接口、同步/异步及失败语义；不是人工任务 |
| 等待外部事件后继续 | `ReceiveTask` | 确认触发接口、恢复事件和超时/补偿要求 |
| 调用独立维护的完整流程 | `CallActivity` | 确认子流程业务键、版本及目标已发布证据；当前导入/迁移会 blocked |
| 流程正常完成 | `EndEvent` | 到达后不再产生任务 |
| 明确取消整个流程 | `TerminateEndEvent` | 只有业务明确“不再修改重报”时使用；不能默认作为驳回出口 |

### 3.3 网关

| 业务场景 | 节点 | 选择边界与必问项 |
| --- | --- | --- |
| 系统按字段自动选择一条路径 | `ExclusiveGateway` | 条件应能互斥并有明确优先级；每个网关恰好一条默认边 |
| 用户在运行时选择一条路径 | `ManualExclusiveGateway` | 确认谁在哪个任务中选择；不用于字段自动判断 |
| 多条独立路径无条件全部执行 | `ParallelGateway` | 确认所有分支及汇合、否决规则 |
| 按组合条件执行一条或多条路径 | `InclusiveGateway` | 确认多命中、默认路径和汇合规则 |

**判断顺序：先问“谁决定路径”，再问“走一条、多条还是全部”。** 不要因为存在多个分支就默认使用人工排他网关。

## 4. 系统判定条件与网关优先级

网关条件不是自由文本。平台按业务实体发布的“条件属性”判定路径，设计器保存连线前会用同一份清单校验表达式，引用了清单之外的变量就保存不了。

因此在设计任何分流之前，必须先读取目标环境发布的条件字段：

```text
eadp bpm graph conditions --env <target> --flow <flow-code>
```

输出中每个条件字段包含：

| 字段 | 含义 | 用途 |
| --- | --- | --- |
| `code` | 引擎变量名，例如 `fileType` | 写进 `groovyUel`，例如 `#{fileType=="销售-合同验收"}` |
| `name` | 中文业务名称，例如 `文件类型` | 写进 `logicUel`，例如 `文件类型=="销售-合同验收"` |
| `initValue` | 引擎校验表达式时使用的初始值 | 判断空值与比较符语义 |
| `remark` | 业务实体对该条件的说明 | 理解字段业务含义 |

同一输出还给出网关选型优先级：

| 优先级 | 节点 | 什么时候用 |
| --- | --- | --- |
| 1（最高） | `ExclusiveGateway` 系统排他网关 | 条件字段能判定的业务分流，一律使用它 |
| 2 | `InclusiveGateway` 系统包容网关 | 确实可能同时命中多条路径，且已确认汇合语义 |
| 3 | `ParallelGateway` 并行网关 | 无条件同时进入多条独立路径 |
| 4（最低） | `ManualExclusiveGateway` 人工排他网关 | 系统条件字段无法判定、必须由人运行时选路 |

**系统排他网关优先级最高**：它由系统字段决定路径，唯一、可复现、可审计。人工排他网关是兜底，不得在系统条件字段可以判定时使用，也不得作为“多个分支”的默认选型。

规则：

- 条件变量必须来自 `eadp bpm graph conditions` 的清单，不得从中文标题、节点名称或其他环境猜测；
- `logicUel` 用条件 `name`，`groovyUel` 用条件 `code`，两者必须表达同一规则；
- 业务需要的判定字段系统没有发布时，先提出“字段缺失”，不要用相近字段顶替；
- 同一个网关内不要混用系统判定与人工选路；
- `validate` 会按同一份清单校验，命中 `CONDITION_VARIABLE_UNKNOWN`、`CONDITION_PROPERTY_UNKNOWN`、`CONDITION_EXPRESSION_MISSING` 时 `designValid=false`。

## 5. 典型组合模式

### 5.1 固定互斥完整路线

一种输入只对应一条完整路线，路线之间不叠加时，可使用一个系统排他网关连接多个条件分支，并保留默认路线。

先证明条件互斥且覆盖完整；若多个角色可以按条件叠加参加，不应使用此模式。

### 5.2 按顺序叠加的可选审批角色

多个角色有固定顺序，且每个角色可独立按条件参加时：

```text
上一个环节
  → 系统排他网关判断角色 A
      ├─ 命中 → A 审批 → 角色 B 判断
      └─ 默认 → 角色 B 判断
```

该模式适合“某些资料需要法务、某些需要财务、部分资料两者都需要”的场景。每个系统排他网关必须有默认边，审批同意后与未命中默认边都进入下一个判断。

不要把这种可叠加规则误画成一个人工排他网关下的若干固定路线。

### 5.3 修改并重审

```text
审批不同意 → 单据修改（Normal + StartUser）→ 经确认的重审入口
```

必须确认：

- 从头重审还是返回指定审批环节；
- 已审批节点是否重新执行；
- 是否允许终止，终止由谁发起。

不得未经确认把“不同意”改成“终止结束”。

### 5.4 多人会签与多个顺序审批

- 同一环节多人共同形成结论：`CounterSign`。
- 多个角色有明确先后顺序：多个 `Approve`。
- 多条独立业务分支同时执行：评估 `ParallelGateway`，不要用会签替代分支建模。

### 5.5 结束后处理

- 自动同步、签章等系统动作：`ServiceTask` 或流程级事件。
- 人工抄送、人工归档：`Normal`。
- 独立维护且已发布的完整流程：`CallActivity`，但当前文件导入/迁移会阻断。

不得为了让校验通过而静默删除这些业务动作或替换节点类型。

## 6. 执行人选择

| 类型 | 使用场景 | 可移植绑定 |
| --- | --- | --- |
| `StartUser` | 发起人本人修改或办理 | 无需人员 code |
| `Person` | 指定员工 | employee code |
| `Position` | 具体岗位实例 | position code，并核对组织上下文 |
| `PositionType` | 按岗位类别动态选人 | position category code |
| `SelfDefinition` | 自定义接口返回执行人 | interface URL，接口类型为 `CUSTOM_PERSON` |
| `PositionTypeAndOrg` | 岗位类别同时受组织约束 | `PositionType` 与 `Org` 两个分片 |
| `AnyOne` | 明确允许任意执行人 | 先确认维度限制，不能作为未知执行人的兜底 |

节点显示名不是绑定依据。例如“经理审批”可能绑定固定岗位、岗位类别或自定义选人接口，必须确认 `executor`，不能从节点名称推断。

## 7. 条件与连线契约

每个条件至少明确：

- 中文业务含义；
- 引擎变量名（取自 `eadp bpm graph conditions`）；
- 数据类型；
- 允许值或枚举；
- 空值如何参与判断；
- 比较符及阈值是否包含等号。

`logicUel` 与 `groovyUel` 必须表达同一条件，变量名不得从中文标题猜测。连线标题与实际表达式冲突时先澄清。

连线底线：

- `Approve`、`CounterSign` 恰好两条出口，其中一条 `uel.agree=true`；
- `ExclusiveGateway`、`InclusiveGateway` 恰好一条 `uel.isDefault=true`；
- `ManualExclusiveGateway` 不强制默认边；
- 全图恰好一个 `StartEvent`，至少一个结束节点，所有连线目标存在；
- 每条路径都有业务解释，不用默认边掩盖未知场景。

## 8. 规范化文件与目标绑定

生成的文件必须为 `eadp.bpm.graph.v1`：

- 页面和接口使用 URL；
- 人员、岗位、岗位类别和组织使用业务 code；
- 不包含外部环境数据库 ID、定义 ID、版本 ID；
- 不直接构造或提交设计器原始 `defJson`；
- 目标流程类型、业务实体、页面和接口骨架先存在，再写图。

外部参考中同名记录不代表目标环境存在；零个或多个候选都必须停止并澄清。

## 9. 校验、预览、写入与验收

```text
eadp bpm graph guide
eadp bpm graph nodes
eadp bpm graph conditions --env <target> --flow <flow-code>
eadp bpm graph validate --env <target> --file <graph.json> --strict
eadp bpm graph import --env <target> --flow <flow-code> --file <graph.json> --strict
eadp bpm graph import --env <target> --flow <flow-code> --file <graph.json> --strict --apply
```

执行要求：

1. 写入前，用代表性业务输入核对预期路径、跳过路径和驳回路径。
2. `validate --strict` 同时满足 `valid=true`、`designValid=true`，并解决全部缺失依赖。
3. 预览核对目标定义及 `create/update/blocked`；意外 `create` 不是“更安全”，可能是定义匹配错误。
4. 用户确认同一预览后再 `--apply`，要求 `verified=true`。
5. 再次预览应为 `unchanged`；草稿在设计器复核后由人发布。

`designValid=true` 只表示结构可保存，不证明业务正确。验收至少覆盖：未命中默认、空值、阈值以下/等于/以上、多条件同时成立、同意、驳回重审、会签/并行和结束后动作。
